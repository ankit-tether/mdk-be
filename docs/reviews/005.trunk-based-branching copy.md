# `mdk-prv` — Gitflow Branching & Release Workflow (Mandatory Release → Main → Develop Merge-Back)

> **Version:** 0.2.0  |  **Date:** 2026-07-12  |  **Status:** Decided (team consensus via Slack) — supersedes v0.1.0 trunk-based proposal below
> **Audience:** All developers contributing to `mdk-prv`
> **Source:** [Slack thread](https://tether-to.slack.com/archives/C0BGANUA6U9/p1783606262426219), channel `C0BGANUA6U9`

---

## Summary / Decision

The team discussed replacing the current **Gitflow** model with trunk-based development (see the original proposal, archived in [Version History](#version-history)). After discussion, the team agreed to **keep Gitflow** rather than switch models.

The one real process gap that was raised — hotfixes landing on a `release/*` branch and never making it back into `develop` (becoming orphaned) — is closed by making the **release → main → develop merge-back an explicit, mandatory step of every release**, not something left to memory.

---

## The Agreed Model

Branches stay as they are today:

```
develop        ← integration branch, all feature work lands here
feature/*      ← branched from develop, merged back to develop
release/*      ← cut from develop when a release is planned; testing/verification/hotfixes happen here
main           ← always reflects the latest released, tagged code
```

```
develop ──●──●──●──●────────────────●── (ongoing feature work)
           \        \                \
          feature/* release/x.y.z ──► main (tag)
                        (hotfixes)        │
                                          ▼
                                   merge back into develop
                                   (mandatory, same release)
```



### The explicit rule this decision adds

> Every `release/*` branch — including any hotfixes applied to it during stabilization — **must** be merged into `main` (and tagged), and `main` **must then be merged back into** `develop`, as one continuous, non-optional part of closing that release. A release is not considered "done" until the merge-back to `develop` has happened.

This is not a new branching model — it is Gitflow with the merge-back written down as a rule instead of an assumption.

---

## Why — The Gap Being Closed

> "I am looking for a failure free flow. Under the current system, hot fixes have gone onto the release branch that never made it onto develop (meaning they become one offs/orphans). This is a hole." — Harrie

The issue was never with Gitflow itself — it was that the merge-back step was implicit and sometimes skipped. Making it a required, checked step removes the failure mode without changing the branching model.

> "Yeah absolutely correct... release goes into main with all the hotfixes, and then main goes to develop to make sure nothing is missing. No need to worry about any orphans or doubled PRs." — Arif_Dewi

> "The proposal isn't an alternative to GitFlow — it is GitFlow (develop / release branch / tagged main, fixes merge back to develop). It just writes down the parts we've been dropping, like the merge-back, so they're rules instead of things we remember." — Ikako

---

## Release Process

1. **Trigger:** Manager confirms all planned tasks for the release are done, and pings a senior developer (any senior dev) to cut the `release/`* branch from `develop`.
2. **Stabilize:** Team tests, verifies, and applies any needed hotfixes directly on the `release/`* branch.
3. **Ship:** `release/`* merges into `main`; `main` is tagged for the release.
4. **Close the loop (mandatory):** `main` merges back into `develop` so every hotfix and release-time change is captured going forward. This step is part of the release, not a follow-up chore.
5. **Mirroring:** Additional steps (e.g., copying to the public repo) continue unchanged — they don't affect the core flow above.

> "People can make mistakes in any process... but if we take care of it, that's really easy to maintain." — Arif_Dewi
