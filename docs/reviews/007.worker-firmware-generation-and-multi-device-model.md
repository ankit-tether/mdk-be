## Q1 — Can a worker really be generated from vendor API docs?

**Yes, confirmed with a real example.** Braiins OS+ (the firmware in question) ships a fully public API:

- **[`braiins/bos-plus-api`](https://github.com/braiins/bos-plus-api)** — gRPC `.proto` definitions, one service per concern (`ApiVersionService`, `MinerService`, `AdvancedSettingsService`, `PoolService`, `CoolingService`, …). Server reflection is enabled, so the surface is fully introspectable (`grpcurl -plaintext miner:50051 describe`).
- **[`braiins/bos-plus-api-demos`](https://github.com/braiins/bos-plus-api-demos)** — working client examples in Go, Python, and Rust.
- The API is explicitly **per-device**: a client opens one gRPC connection to one miner's IP on port `50051`. There is no fleet/multi-device concept anywhere in the spec — which is exactly the shape a worker's translation layer expects (§Q2 below).

This validates the model in [`Workers in MDK: a simpler model.md`](../Workers%20in%20MDK_%20a%20simpler%20model.md): a worker is a declarative contract + a thin translation layer, both of which map 1:1 onto what a proto/OpenAPI/Modbus spec already contains. Nothing about Braiins requires bespoke reverse-engineering — an agent can read the `.proto` files directly.

### The generation workflow

```text
   Vendor API docs                 Agent                        Output
  (Braiins .proto files)     ┌───────────────┐        ┌─────────────────────────────┐
  ───────────────────────►   │  reads spec +  │  ───►  │ mdk-contract.json           │
                              │  mdk-contract  │        │  (declarative: readings,     │
                              │  .schema.json  │        │   commands, error codes)     │
                              │  + Worker base │        ├─────────────────────────────┤
                              │  interface     │  ───►  │ hardware.js                 │
                              └───────────────┘        │  (thin translation: one       │
                                                        │   gRPC/HTTP/Modbus call        │
                                                        │   per contract action, for      │
                                                        │   ONE device)                    │
                                                        └─────────────────────────────┘
```

The agent's job is deliberately narrow — it only ever produces **two artifacts**, matching [`hld.md` §6.2](../hld.md#62-integration-workflow):

1. **`mdk-contract.json`** — filled in directly from the spec (every `AdvancedSettingsService` field becomes a telemetry/config entry, every RPC becomes a command, every documented error becomes a `troubleshooting` entry).
2. **A single-device translation class** implementing the two required hooks (`onTelemetryPull`, `onCommand`) that map a contract action to exactly one gRPC/HTTP/Modbus call against exactly one device connection.

Everything else — HRPC plumbing, registration, health pings, the telemetry poll loop, **and running many of these in parallel** — is inherited for free from `@tetherto/mdk-worker` (per [`hld.md` §4.4.2](../hld.md#44-workers--device-integration-handlers) and the `Thing`/`ThingManager` split already implemented per [`003.mdk-worker-package.md`](./003.mdk-worker-package.md)). The agent never touches that layer, which is exactly why this is a minutes-not-days task.

**Action item:** write a short "generation playbook" (prompt template) that bundles `mdk-contract.schema.json` + the `@tetherto/mdk-worker` interface + a worked example (Whatsminer) as context, so pointing it at any firmware's docs reliably produces a compliant worker. Track as follow-up to this doc.

## Q2 — How does one worker manage many devices, when the vendor API is per-device?

This is the question left open in Slack. Ankit's framing was correct and the resolution below reconciles it with Gio's "ATM workers run many devices in parallel":

> Both are true at once. The vendor API being per-device does **not** force one-worker-per-device. It forces one-**connection**-per-device. A worker process holds a *pool* of N such connections — one per configured device — and fans out to the right one by `deviceId`. No new worker architecture is needed; this is exactly the `Thing` / `ThingManager` split that already exists in the codebase today.

### The shape

```text
┌──────────────────────────────────────────────────────────────────┐
│                    braiins-worker (ONE process)                  │
│                                                                    │
│   ThingManager (inherited from @tetherto/mdk-worker, unmodified) │
│   - owns the deviceId → instance map                              │
│   - routes command.request / telemetry.pull by deviceId           │
│   - runs the shared telemetry-poll scheduler                      │
│                                                                    │
│        ┌────────────┐   ┌────────────┐   ┌────────────┐          │
│        │  Miner      │   │  Miner      │   │  Miner      │  ...   │
│        │  (AM001)    │   │  (AM002)    │   │  (AM003)    │        │
│        │  1 gRPC     │   │  1 gRPC     │   │  1 gRPC     │        │
│        │  conn:50051 │   │  conn:50051 │   │  conn:50051 │        │
│        └──────┬──────┘   └──────┬──────┘   └──────┬──────┘        │
└───────────────┼─────────────────┼─────────────────┼───────────────┘
                 ▼                 ▼                 ▼
             AntMiner #1       AntMiner #2       AntMiner #3
           (Braiins OS+)      (Braiins OS+)      (Braiins OS+)
```

Concretely, per device the agent-generated `Miner` class holds **exactly one** gRPC channel to **exactly one** IP:port — matching the vendor API 1:1, which is what makes it generatable from the spec in the first place. The `ThingManager` (already generic, already built, not regenerated per firmware) is what turns N of those single-device instances into "one worker managing many devices."

This directly answers both parts of Ankit's original question:

| Question | Answer |
|---|---|
| Does the worker aggregate across devices? | **No.** Confirmed — a `Miner` instance only ever talks to its one device. Aggregation, rollups, and fleet logic stay entirely in the Gateway (App Node), per [`Workers in MDK: a simpler model.md`](../Workers%20in%20MDK_%20a%20simpler%20model.md#the-idea) and [`hld-app-node-plugins.md`](../hld-app-node-plugins.md) §5.2. |
| Does "one worker, many devices" require rewriting the per-device translation for multiplicity? | **No.** The translation layer an agent generates is single-device only, exactly matching the spec. Multiplicity is handled entirely by the inherited Manager — zero firmware-specific code deals with more than one device at a time. |

### Why this isn't "one worker per device"

If the agent had to write the fan-out logic itself, Ankit's alternative (one worker per device) would in fact be simpler to generate — but it doesn't scale operationally: thousands of OS processes to supervise, register, and keep alive (per [`Workers in MDK: a simpler model.md`](../Workers%20in%20MDK_%20a%20simpler%20model.md#the-idea) and Gio's point in Slack). Because the fan-out is boilerplate owned by `@tetherto/mdk-worker` and never touched by the generated code, we get the operational benefit of process consolidation **without** costing the agent any extra generation complexity. This is why the existing `Thing`/`ThingManager` pattern is worth keeping and standardizing on rather than introducing a new per-device-process model.

### Scaling beyond one process

Splitting still exists — it's a **deployment/config** decision, not a code change (already documented, just re-affirming it applies to firmware workers too):

| Scale | Layout |
|---|---|
| 1–50 devices of one firmware | One `braiins-worker` process, N `Miner` instances |
| 50–500 devices | Multiple `braiins-worker` processes, split by rack, each with its own device subset |
| 500+ devices | Worker-per-rack/cluster, per [`hld.md` §7.1](../hld.md#71-routing-and-ownership-parallel-workers) |

ORK's Worker Registry already handles this — each process registers only the `deviceId`s it owns; ORK routes deterministically. No worker code changes as device count grows, only the config listing which devices a given process instance manages.
