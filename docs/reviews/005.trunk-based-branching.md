# `mdk-prv` — Trunk-Based Development & Tag-Driven Releases

> **Version:** 0.1.0  |  **Date:** 2026-06-30  |  **Status:** Proposed
> **Audience:** All developers contributing to `mdk-prv`

---

## The Proposal

Use **trunk-based development**: all work lands on `main` via short-lived branches (hours to 1–2 days, not weeks). Versions are never separate long-lived branches — they are **git tags** on `main`. There are no `release/x.y.z` or `v1-stable` branches.

---

## Why — The Problem With Long-Lived Branches

The current repo has `main`, `develop`, `release/0.3.0`, `staging`, and feature branches that can live for weeks. The cost:

| Pain | Cause |
|---|---|
| Merge conflicts at integration time | Branches diverge from `main` while the world keeps moving |
| "Merge week" overhead | The longer a branch lives, the more semantic drift accumulates |
| Stale branches | Branches start, get abandoned mid-feature, and become noise |
| Unclear what is shippable | Multiple long-lived branches mean no single source of truth |
| CI runs on branches nobody is watching | Failures get discovered late or ignored |

The cost of a merge is **not linear** in time — a two-day branch is a normal merge; a two-week branch is a project.

---

## How Trunk-Based Development Works

### Core rule
Every developer works on a short-lived branch off `main`. It merges back to `main` within a day or two, then is deleted. `main` is always in a deployable state.

```
main  ──●──────●──────●──────●──────●──── (always shippable)
           \  /    \  /   \  /
            ● feat   ● fix  ● refactor
           (hours–2 days max)
```

### How to ship a version without a release branch

Tag `main` when it's ready to ship. The tag *is* the release.

```bash
# When main is ready for v0.4.0
git tag -a v0.4.0 -m "release: v0.4.0"
git push origin v0.4.0

# CI picks up the tag → builds, publishes npm packages, creates GitHub Release
```

No branch needed. No merge back. The tag is permanent and immutable on that commit.

### How to handle large features that take > 2 days

Two tools make this work without long-lived branches:

1. **Feature flags** — merge incomplete code behind an off switch. The branch closes when the *slice* is done, not when the *feature* is done.

2. **Stacked PRs** — break a multi-day refactor into 4–5 small reviewable PRs that chain on top of each other. Each merges to `main` independently. The feature emerges from the stack.

---

## Benefits

| Benefit | Detail |
|---|---|
| **No merge conflicts** | Branches never live long enough to drift far from `main`. Conflicts are small and caught immediately. |
| **`main` is always shippable** | Any commit on `main` can be tagged and released. No "stabilisation sprint" needed. |
| **Faster feedback** | CI runs on every merge to `main`. Issues surface within minutes, not at the end of a release cycle. |
| **Simpler branch hygiene** | One permanent branch (`main`). Everything else is short-lived and deleted on merge. |
| **Tags as releases** | `v0.3.0`, `v0.4.0` are immutable points in history. Easy to compare diffs between releases: `git diff v0.3.0...v0.4.0`. |
| **Better CI/CD** | A single branch to watch means CI is always warm, always meaningful. Deploys to staging/prod trigger on tags, not branches. |
| **Team cohesion** | Everyone works on the same shared history. No developer is isolated on a week-old fork of reality. |

## What Replaces Each Current Branch

| Current branch | Replacement |
|---|---|
| `release/0.3.0` | Git tag `v0.3.0` on `main` |
| `staging` | CI deployment target triggered by tag pattern `v*` |
| `develop` | Eliminated — `main` plays this role |
| Long feature branches | Short-lived branch (≤ 2 days) + feature flag if needed |

## Branch Naming Convention

Since all branches are short-lived, keep names simple and descriptive:

```
feat/<topic>          # new feature slice
fix/<topic>           # bug fix
chore/<topic>         # tooling, deps, CI
docs/<topic>          # documentation only
refactor/<topic>      # code restructure
```

No version numbers in branch names. Versions live only in tags.

## Release Workflow (Tag-Driven)

```bash
# 1. Confirm main is green
git checkout main && git pull

# 2. Bump versions across workspace packages
npm version minor --workspaces --no-git-tag-version
# (or: patch / major depending on the release)

# 3. Commit the version bump
git add . && git commit -m "chore(release): bump versions to 0.4.0"

# 4. Tag and push
git tag -a v0.4.0 -m "release: v0.4.0"
git push origin main --follow-tags

# CI takes it from here → publish npm packages → create GitHub Release
```

---

## What CI Should Do on a Tag

```yaml
# .github/workflows/release.yml (sketch)
on:
  push:
    tags:
      - 'v*'

jobs:
  publish:
    steps:
      - npm ci
      - npm test --workspaces
      - npm publish --workspaces --access public
      - gh release create ${{ github.ref_name }} --generate-notes
```

---

## Requires

- **Fast CI** — trunk-based development only works if the feedback loop on `main` is short (target: < 10 minutes for lint + test).
- **Test coverage** — `main` must stay green. No merging red PRs.
- **Feature flags** for work that spans multiple days (can be as simple as a config option or an env var — no external service required).
- **PR reviews** — short branches still go through review; they are just small enough to review in one sitting.
